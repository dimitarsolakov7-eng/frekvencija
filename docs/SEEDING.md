# Demo audio, development seed and first admin

Three local scripts prepare a development project. All of them run with `tsx` from `scripts/`
(`scripts/package.json` puts them in ESM mode) and read `.env.local`, then `.env`, from the project
root. Variables already set in the shell win. They need a supported Node.js version
([SETUP.md §1](SETUP.md#1-requirements)). An older Node.js stops with a clear message instead of
`process.loadEnvFile is not a function`.

| Command | What it does | Network |
| --- | --- | --- |
| `npm run demo:audio` | Generates the synthetic demo audio into `supabase/seed/audio/` | none |
| `npm run seed:dev -- --dry-run` | Prints what the seed would do | none |
| `npm run seed:dev -- --yes` | Writes demo genres, venues, users, tracks and announcements | Supabase (secret key) |
| `npm run admin:create -- <email> [--link]` | Invites or promotes a platform admin | Supabase (secret key) |

> **All demo audio is synthetic and labelled as such.** The music files are generated tone loops,
> not real music. The announcements are computer speech (Windows SAPI) or chime placeholders, not
> recordings of a real person. Every file says so in its ID3 tags (title ends in "(synthetic)",
> "(computer voice)" or "(not speech)"; the artist is "<platform name> Test Signal"; the album and
> comment repeat the notice), and `manifest.json` marks every entry `"synthetic": true`.

## 1. Generate the demo audio

```bash
npm run demo:audio               # Windows: announcements spoken by Windows SAPI
npm run demo:audio -- --no-sapi  # chime placeholders instead of speech (any OS)
```

It takes about 1–2 minutes and writes:

| Path | Content |
| --- | --- |
| `music/test-loop-NN-<genre>.mp3` | 21 synthetic loops: House ×6 (01–06), Deep House ×3 (07–09), Lounge ×4 (10–13), Jazz ×3 (14–16), Balkan Hits ×2 (17–18), Chillout ×3 (19–21). Titled "Test Loop NN — Genre (synthetic)". Each is 20–40 s long, so testing "an announcement after every 4 completed tracks" takes about two minutes. Mono, 44.1 kHz, 96 kbps (about 7 MB in total). |
| `announcements/<venue>-<template>.mp3` | 3 per venue, from the app's templates (`src/lib/announcements/templates.ts`). **EmeraldBar** (voice: Microsoft David): "Welcome to EmeraldBar. Enjoy the music." (welcome), "You’re listening to EmeraldBar Radio." and "Good music. Good company. This is EmeraldBar Radio." (rotation). It speaks the `spoken_text` form, which uses the pronunciation "Emerald Bar". **Hotel Aurora** (voice: Microsoft Zira): the same templates with its own names. Mono, 44.1 kHz, 128 kbps. |
| `manifest.json` | Describes every file (see below). The seed and the development audio route read it. |

How the files are made:

- **Loops**: chord progression, bass, arpeggio and soft percussion, with a different tempo, key,
  groove and timbre per genre (for example House: 4-on-the-floor at ~122 bpm; Jazz: walking bass and
  a swung ride; Chillout: slow pads, no drums). Each loop is deterministic by its seed: re-running the
  generator produces byte-identical files, so the repository diff stays empty.
- **Speech**: Windows PowerShell 5.1 `System.Speech` renders a WAV, which is converted to MP3. The
  text is passed through an environment variable, so it is never interpreted as a command. On a
  machine that is not Windows, or that has no SAPI voices, or with `--no-sapi`, each announcement
  becomes a **chime placeholder**. The chime melody is distinct per venue (EmeraldBar: rising bell
  notes; Hotel Aurora: falling marimba notes) and per announcement. The generator prints why SAPI was
  not used.
- **Loudness**: every file is normalised to −16 LUFS integrated (ITU-R BS.1770), with a −1 dBFS
  sample-peak ceiling (`docs/research/audio-tooling.md` §8).
- **Verification**: before a file is written, it must pass a strict MPEG frame walk (right format,
  no junk bytes, expected length) and the app's upload validator `validateMp3()` (including its
  codec check and title/artist read-back). The seed later checks every file's size and SHA-256
  against the manifest.
- Stale `.mp3` files that are no longer in the catalogue are deleted from both folders.

### `manifest.json`

```jsonc
{
  "version": 1,
  "synthetic": true,
  "notice": "Synthetic test audio generated by `npm run demo:audio` …",
  "entries": [
    {
      "kind": "track",
      "id": "test-loop-01-house",            // unique; also the file's base name
      "file": "music/test-loop-01-house.mp3", // relative to supabase/seed/audio
      "title": "Test Loop 01 — House (synthetic)",
      "artist": "Frekvencija Test Signal",
      "genre": "house",                       // genre slug
      "durationSeconds": 31.27,               // as validateMp3() reports it
      "bytes": 375661, "sha256": "…",
      "bitrateKbps": 96, "sampleRateHz": 44100, "channels": 1,
      "generator": "synthetic-tones",
      "style": { "mood": "bright", "bpm": 123, "key": "A" },
      "synthetic": true
    },
    {
      "kind": "announcement",
      "id": "emeraldbar-welcome-enjoy",
      "file": "announcements/emeraldbar-welcome-enjoy.mp3",
      "business": "emeraldbar",               // demo venue key: "emeraldbar" | "hotel-aurora"
      "templateKey": "welcome_enjoy",         // key in ANNOUNCEMENT_TEMPLATES
      "placement": "welcome",                 // welcome | rotation | both
      "text": "Welcome to EmeraldBar. Enjoy the music.",
      "spokenText": "Welcome to Emerald Bar. Enjoy the music.", // null when identical to text
      "generator": "windows-sapi",            // or "chime-placeholder"
      "voice": "Microsoft David Desktop",     // null for chime placeholders
      "…": "same common fields as tracks"
    }
  ]
}
```

The schema, including checks for unique ids and matching paths, is in `scripts/lib/manifest.ts`.

## 2. Seed a development project

Prerequisites:

- **A Supabase project to seed.** This can be a hosted *development* project, or a local stack.
  - For a local stack, install the Supabase CLI and Docker yourself (neither is a project
    dependency). This repository ships no `supabase/config.toml`, so run `supabase init` once in the
    project root; it adds the file and keeps `supabase/migrations/`. Then run `supabase start`, which
    applies the migrations.
  - Copy the API URL (`http://127.0.0.1:54321` by default) and the keys printed by `supabase status`
    into `.env.local`.
- **Every file in `supabase/migrations/` is applied, in filename order.** There are currently four,
  including `20260926000100_frekvencija.sql` (see [SETUP.md §4](SETUP.md#4-apply-the-database-migrations)).
  The app needs all of them: the venue player reads `businesses.business_type`, and the homepage and
  Settings read `platform_settings` and the genre covers. The seed checks this first. If a table or
  column from the migrations is missing, it names it and stops before writing anything.
- **`.env.local`** has `NEXT_PUBLIC_SUPABASE_URL` and `SUPABASE_SECRET_KEY` (legacy fallback:
  `SUPABASE_SERVICE_ROLE_KEY`).
- **The demo audio exists.** Run `npm run demo:audio` first; otherwise the seed stops and tells you to.

```bash
npm run seed:dev -- --dry-run        # the plan; no network calls, nothing written
npm run seed:dev -- --yes            # local Supabase (localhost / 127.0.0.1 / [::1])
npm run seed:dev -- --yes --allow-remote   # a hosted *development* project
```

### Safety rules

The seed refuses to run, writes nothing, and prints every reason when:

- `NODE_ENV` is `production`. No flag overrides this.
- `--yes` is missing.
- `NEXT_PUBLIC_SUPABASE_URL` is not `localhost`, `127.0.0.1` or `[::1]` and `--allow-remote` is missing.
  The seed creates demo users and prints their passwords, so it must not reach a real project by
  accident.
- The database lacks a table or column from `supabase/migrations/`, for example because
  `20260926000100_frekvencija.sql` was not applied. The seed detects this while reading the existing
  rows, before anything is written.
- The plan has a **conflict**:
  - A business named EmeraldBar or Hotel Aurora exists that is not seed data. Real venues are never
    modified.
  - Two demo copies of the same venue exist.
  - A demo user email belongs to a platform admin, or to a member of another venue.
  - The manifest refers to an unknown genre or venue.

Secrets are never printed. The only credentials shown are the one-time passwords of users created in
**this** run (see below).

### What it creates

| Kind | Rows |
| --- | --- |
| Genres | House, Deep House, Lounge, Jazz, Pop, Rock, R&B, Balkan Hits, Chillout (sort order 1–9, with descriptions). **Jazz** and **Balkan Hits** have `available_to_all = false`. Pop, Rock and R&B get no tracks, so they exercise the player's empty-genre state. |
| Businesses | **EmeraldBar**: type **Bar**, station "EmeraldBar Radio", pronunciation "Emerald Bar", contact `demo+emeraldbar@example.com`. **Hotel Aurora**: type **Hotel**, station "Hotel Aurora Radio", contact `demo+hotel-aurora@example.com`. Both are active, in English, at announcement volume 1.00. Both play an announcement after every N completed songs, where N is the platform default from **Settings** (`platform_settings.default_announcement_every_n_tracks`: 4 unless changed, or 4 if the row is missing), just as **Add business** prefills it. The example.com contact address is the **seed marker**. |
| Exclusive access | Balkan Hits → EmeraldBar only. Jazz → Hotel Aurora only. |
| Users | An admin (`--admin-email`, else `SEED_ADMIN_EMAIL`, else `admin@example.com`), promoted to `platform_admin`. One venue user each: `SEED_EMERALDBAR_EMAIL` (default `emeraldbar@example.com`) and `SEED_AURORA_EMAIL` (default `hotel-aurora@example.com`), with their `business_members` rows. New users are created with `email_confirm: true` and a random 24-character password. |
| Tracks | The 21 loops, uploaded to bucket `music` at `tracks/{track_id}/{random}.mp3`. Each has its duration, bitrate and sample rate from the manifest, `created_by` = the admin, and a `track_genres` link. |
| Announcements | Each venue's 3 announcements, uploaded to bucket `announcements` at `{business_id}/{announcement_id}/{random}.mp3`. They are `status = active`, `source = upload`, approved now by the admin, have `branding_version` equal to the venue's, `needs_review = false`, the manifest placement, `template_key`, `text` and `spoken_text`. They are playable immediately. |

The seed then prints a summary and the **one-time passwords** of the users it created. Store them in
a password manager: they are not saved anywhere and are never shown again. Users that already
existed keep their passwords, and none is shown for them. If a later step fails, the passwords of
the users created so far are still printed.

**How the demo venues are labelled.** The names stay exactly "EmeraldBar" and "Hotel Aurora", because
the demo announcements speak them ("Welcome to EmeraldBar. Enjoy the music."). The `businesses` table
has no notes field, and the seed adds no columns, so there is no "Example venue" text on the row itself.
The demo data is recognisable by:

- the contact email `demo+…@example.com`. It is the venue's **Contact email** on its Profile tab, and
  searching the business list for `example.com` (the search covers contact emails) finds the demo
  venues;
- the staff accounts, named "EmeraldBar demo user" and "Hotel Aurora demo user", with `@example.com`
  sign-in emails;
- the tracks, all titled "Test Loop NN — Genre (synthetic)" and credited to "Frekvencija Test Signal".

**Platform settings are never written.** The seed only reads `platform_settings`, to get the default
announcement frequency. Contact details, the privacy policy and the terms are the owner's
configuration. Placeholder values would appear on `/request-access`, `/privacy`, `/terms` and the
venues' Help page as if they were real, so they stay empty. Until you fill them in at
`/admin/settings`, the Help page shows no contact details, and `/privacy` and `/terms` say they
haven't been published yet. To review those screens with example values, use
`/dev/preview/radio/help` and `/dev/preview/settings`.

### Re-running (idempotent)

A second run creates nothing new. Existing rows are matched as follows:

| Row | Matched by |
| --- | --- |
| Genres | slug (else the same name, case-insensitive) |
| Businesses | name **and** the seed-marker contact email |
| Tracks | exact title (e.g. "Test Loop 07 — Deep House (synthetic)") |
| Announcements | venue + `template_key`. An existing one without audio gets the audio attached and is approved. |
| Users | email |
| Access and genre links | inserted with "on conflict do nothing" |

The seed never changes existing rows otherwise, with one exception. A demo venue that still has the
business type **Other** (the column default, meaning it was seeded before business types existed)
gets its demo type, Bar or Hotel. The plan shows this as "reuse, set type". The type is not part of
the branding, so the venue's announcements are not flagged for review. A type chosen in the admin is
kept. Existing demo venues also keep their announcement frequency.

If an admin disabled a demo track, deactivated a venue, changed a demo venue's type, or an
announcement needs review after a branding change, the seed leaves it that way and lists it under
"Notes".

Every object is uploaded before the row that points at it. If the row cannot be written, the object
is removed again. A failed run can therefore simply be re-run, and it continues where it stopped.

### Removing demo data

Delete the demo venues, tracks and genres in the admin UI, and the demo users in the Supabase
dashboard (Authentication). Deleting rows does **not** delete Storage objects. Remove them in the
dashboard (buckets `music` → `tracks/…`, and `announcements` → `<business_id>/…`) or with the
Storage API. SQL cannot delete Storage objects.

## 3. Create the first platform admin

```bash
npm run admin:create -- owner@yourcompany.com          # invite by email, then promote
npm run admin:create -- owner@yourcompany.com --link   # print a one-time invite link instead
```

- **Existing user**: promoted to `platform_admin` (`profiles.role`). Their password is untouched.
- **New user**: `auth.admin.inviteUserByEmail(email, { redirectTo: NEXT_PUBLIC_SITE_URL })`, then
  promoted. The invite email must use the `token_hash` **Invite user** template from
  [SETUP.md §5](SETUP.md#5-configure-authentication), so its link opens `/auth/confirm` and then
  `/reset-password`. A local stack does not use the dashboard templates: it sends its own default
  emails (templates live in `supabase/config.toml`), so use `--link` there.
- **`--link`**: uses `auth.admin.generateLink({ type: "invite" })` and prints
  `SITE_URL/auth/confirm?token_hash=…&type=invite&next=/reset-password` once, with a warning. No email
  is sent. Use it when Supabase's default SMTP cannot reach the address (it only delivers to project
  team members, 2 per hour). Deliver the link privately. It works once and expires with the project's
  Email OTP expiration (default 1 hour). For an existing account that has not been confirmed yet,
  `--link` issues a fresh invite link.
- The script never sets or prints passwords. `NEXT_PUBLIC_SITE_URL` is required for a remote
  project. For a local one it defaults to `http://localhost:3000`.
- If promotion fails after the invite was sent, run the same command again. It then finds the user
  and promotes them.

## 4. Tests

The planning, safety, audio and invite logic is unit-tested without network access. This includes
seed runs against an in-memory Supabase fake. The fake checks idempotency, cleanup after a failed row
write, the conflict refusals, the business types (including fixing old demo rows), the platform-default
announcement frequency, and the refusal when a migration is missing:

```bash
npx vitest run scripts/tests   # also included in `npm test`
```
